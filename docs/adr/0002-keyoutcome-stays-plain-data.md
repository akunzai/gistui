# KeyOutcome stays a plain data enum; only the async-response side deepens

`KeyOutcome` (`src/tui/mod.rs`, 44 variants), `dispatch_outcome`'s match arms (`src/tui/dispatch.rs`), `BgTaskOutcome` (`src/tui/bg.rs`, 24 variants), and `Jobs::on_action_outcome`'s `on_*` handlers each grow one entry per user action — adding one fire-and-forget action touches all four (2026-07 architecture review, candidate A). We considered collapsing all four into a single job-description interface carried by `KeyOutcome` (e.g. a boxed closure describing what to spawn and how to absorb it).

We decided to scope the collapse to the **async-response side only** — `BgTaskOutcome` plus `Jobs::on_action_outcome`'s `on_*` handlers — and leave `KeyOutcome` and `dispatch_outcome`'s match arms as plain data. `docs/agents/architecture.md` documents `handle_key` (which produces `KeyOutcome`) as the pure, unit-tested layer, while `BgTaskOutcome` / `Jobs::on_action_outcome` are explicitly impure thin-IO, not unit-tested by design. The deletion test diverges for the two sides: deleting `BgTaskOutcome`'s per-variant shape and inlining the "apply result to state" logic as a closure built in `dispatch.rs` just moves complexity, at no cost — that side was never a test surface. Deleting `KeyOutcome`'s data shape in favour of an opaque closure would remove `handle_key`'s equality/pattern-match test surface outright — complexity wouldn't move, test coverage would disappear. `spawn_action` / `spawn_gist_fetch_action` (`src/tui/bg.rs:1175-1207`) already expose a generic closure interface on the spawn side; the remaining duplication is concentrated in the enum-plus-match-per-variant shape of `BgTaskOutcome` and `on_action_outcome`, not in `KeyOutcome`.

**Revisit if**: a case shows `handle_key`'s tests never actually depend on `KeyOutcome`'s data shape (e.g. tests only assert side effects, never match on payload fields), or the `KeyOutcome` variant count itself is shown to cause a concrete bug — narrow scope to that case at that point, not by reopening the whole boundary.

**Shipped as #375.** The enum-plus-match is gone (`spawn_action(run, apply)` + a generation-guard shell). Apply was not inlined into `dispatch.rs`: by then #298 had made the `on_*` handlers a unit-test seam, so the "never a test surface" premise no longer held. The `KeyOutcome` half of this ADR is unchanged.

**Apply handlers left `Jobs` as #383.** The `on_*` apply seam stayed named and unit-tested; it moved out of `impl Jobs` onto the screen (or gist-mutation) module that owns the state it mutates. `ActionApply` narrowed to `FnOnce(&mut AppState)`. Apply only marks stale; only the registry spawns. `KeyOutcome` / `dispatch_outcome` stay plain data.
